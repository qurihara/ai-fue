# 草稿v2に現れるすべての数値の検算

対象は `paper/cipherflute_wiss2026_v2_draft.md`（2026年7月30日の白紙書き直し版）である。
本文に現れる数値を1つずつ洗い出し、先行研究の数値は `related_work_survey/PAPER_REVISION.md` の
「使う数値」の表と `raw2/f6-key-numbers.md` と `raw3/` に照らし、本研究自身の数値は
`fue/` の実装コードと `docs/cipher/cipher_config.json` と旧版 `paper/cipherflute_wiss2026_v1.2.docx`
に照らした。符号化器は実際に動かして本数とビット数を確かめた。

判定は「正しい」「誤り」「確認できない」の3つである。誤りには正しい値を書いた。

---

## 0. 結論

**投稿前に必ず直すべき誤りが7件ある。** うち3件は本研究自身の数値であり、
実装を読めば誰でも確かめられるものである。とくに較正定数（3.1節）は、
論文に書かれた値で管長を計算すると実際に印刷した笛より20ミリメートル以上短くなる。

一方、5章の実測値は15項目すべてが旧版と一致した。log₂11 ≈ 3.46ビット、
1本あたりの減り0.13ビット、カード8本20.8ビット、本立て36本64ビット、
スプール49本128ビットは、いずれも符号化器を実際に走らせて再現できた。
2キロヘルツ帯で1セント約1.2ヘルツも正しい。

## 1. 必ず直すべき誤り

### 誤り1（3.1節・161行目）　較正定数 A = 91891.5、e = 14.23 は外形統一版のものではない

草稿の記述は次のとおりである。

> 日用品への埋め込みに用いた外形統一版では *A* = 91891.5、*e* = 14.23 である
> 【要確認：`fue/cipher_codec.py` の既定値。…】

**判定は誤りである。** この値は外形統一版の較正ではない。

根拠は3つある。

第一に、実際に印刷する管の長さを決めているのは `fue/mini10.py` の `length_for_note` であり
（`fue/cipher_card.py` 61-62行目、`fue/spool_128bit.py` 96-97行目、`fue/cipher_cardpair.py` が
いずれもこれを呼ぶ）、その較正は `fue/mini10.py` 27-45行目の `_load_calib` が
`out/cipher_mini10_calib.txt` から読み込む。その中身は

```
A=87985.1
e=-10.010
```

であり、ファイル冒頭の注記に「CipherFlute mini10 外見統一版(uniform_flute)の較正。
2026-07-28 の較正コーム36本からフィット」「実測長で当てはめると12音すべてが1つの式に乗る
（残差 11.3 cent, 30本）」と書いてある。**これは草稿5.1節が述べている当てはめそのものである。**

第二に、`fue/cipher_codec.py` の `calib_k = 91891.5`、`calib_delta = 14.23`（34-35行目）は
`freq_to_length`（129行目）でしか使われず、その戻り値は `EncodeResult.lengths` として
表示に出るだけである。形状生成には一切使われていない。

第三に、91891.5 と 14.23 の出どころは `README.md` の83行目と108行目にある。
「2026/7/1にH2Dで管長40/70/100/130mmの…4本測定、RMS 0.28mm」と書かれており、
mini10ヘッドではなく初期の直管の較正である。同じ値は `fue/compact.py`、`fue/fold.py`、
`fue/revolver.py`、`fue/plenum.py` にも定数として散らばっている。

数字で確かめると差は決定的である。C7（2093.0ヘルツ）に対して、

| 式 | 得られる管長 |
| --- | --- |
| f = 91891.5/(L+14.23)（草稿の値） | 29.67 mm |
| f = 87985.1/(L−10.010)（実装が使う値） | 52.05 mm |

実際に `fue/mini10.py` で生成した笛のC7の外形長は52.05ミリメートルである
（trimeshで境界箱を測って確認した）。草稿の値では22ミリメートル短い。

**直し方。** 3.1節を「外形統一版では *A* = 87985.1、*e* = −10.010 である
（`out/cipher_mini10_calib.txt`。5.1節の当てはめで得た値である）」と書き換える。
式の向き（f = A/(L+e)）は実装と一致しているので変えなくてよい
（`freq_to_length` は L = A/f − e を返し、これは f = A/(L+e) と同値である）。
厚壁ヘッドの A = 86718、e = −11.81 は旧版5.1節の記述と一致しており、そのままでよい。

なお `PAPER_REVISION.md` の179行目が同じ誤りを含んでいるので、そちらも直したほうがよい。

### 誤り2（3.7節・221行目）　SLIP-39の200ビットは笛64本ではなく75本である

草稿の記述は次のとおりである。

> 業界標準のSLIP-39 [12] に準拠すれば、断片1つが200ビットとなり笛64本を要するが、…

**判定は誤りである。正しくは75本である。**

`REVIEW_AND_REPOSITIONING.md` の139行目は
「論文自身の符号化器で計算すると、**168ビットは笛64本、200ビットは笛75本**になる」と
書いている。すなわち64本に対応するのは正味の168ビット（前置き40ビット＋断片値128ビット＋
詰め物2ビットから検査符号30ビットを除いた分）であって、200ビットではない。
`PAPER_REVISION.md` の187行目にある「承認済みの文面」の時点でこの取り違えが混入しており、
草稿はそれをそのまま引き継いでいる。

符号化器で再計算して確かめた。12スロット・隣接同音禁止では素数体は GF(11) であり
（`fue/cipher_codec.py` 291-305行目の `_wire_params` が `p = _prime_below(m-1) = 11` を返す）、
ブロックあたりの検査2記号でブロック長は8記号である。

- 200ビット＝25バイト → データ58記号 → 8ブロック → 符号語74記号 → 基準笛込み**75本**
- 168ビット＝21バイト → データ49記号 → 7ブロック → 符号語63記号 → 基準笛込み**64本**

**直し方。** 「断片1つが200ビットとなり笛75本を要する」に直すか、
「正味168ビットで笛64本、検査符号まで含めた200ビットなら笛75本」と書き分ける。
どちらにしても円盤1枚26本の上限（5.6節）では2枚に収まらず3枚を要する点は変わらない。

### 誤り3（表1・149行目、および2.1節83行目）　本研究の128ビットを「実証容量」として並べている

表1の見出しは「先行研究との比較（実証容量は原典の記載による）」であり、
本研究の行に「**3.5 bit/本、計128 bit**」と書いてある。しかし5.3節（301行目）は
自ら次のように書いている。

> **128ビットの構成については、片側24本の発音と、仮の基準に対する相対の位置が
> 設計どおりであることを確認した段階である。49本を通した復号は未実施である。**

**同じ論文の中で矛盾している。** 2.1節の83行目「本研究は…128ビットに到達する位置にある」も
同じ問題を抱えている。`PAPER_REVISION.md` の28行目は
「実証していないことを実証したと書くのは、引用漏れよりも重い正確性の失敗である」と
明記しており、旧版で外部評価に指摘された当の失敗をそのまま繰り返す形になっている。

**直し方。** 表1の本研究の行を「3.5 bit/本。実証は20.8 bit（カード）、設計は128 bit（未通し）」の
ように書き分けるか、「実証容量」の列名を本研究の行だけ注で断る。
2.1節の「128ビットに到達する位置にある」も同様に弱める。

### 誤り4（表3・271行目、および3.7節223行目）　実装した2-of-3は各128ビットではない

表3は次のように書いている。

| 層 | 量 | 守る力 |
| --- | --- | --- |
| 秘密分散（2-of-3） | 断片は各128 bit | 128 bit |

3.7節（223行目）も「**本研究の実装は後者である。** 2-of-3を3つの異なる日用品に分けているため、
どの物体が何番目の断片であるかは物体自身が語る」と書いている。

**判定は誤りである。** 実際に作った2-of-3は `out/bookstand_v3_shares.txt` に記録されている。

```
# 秘密 260729（11進6桁 = 1,6,8,9,8,7）を、3台のうち2台で復元できるように分けた。
#   1台目 断片 10,8,1,6,10,7
# 台の番号は、正面の底板の左端に彫った数字（1/2/3）で見分ける。
```

すなわち、

1. 断片は記号6個＝**20.8ビット**であって128ビットではない（`fue/threshold.py` 107行目の
   既定も `--width 6`＝20.8ビットである）。
2. 担体は「3つの異なる日用品」ではなく、**同じ設計の本立て3台**である。
3. メンバー番号は物体の形ではなく、**底板に彫った数字**で見分けている。

3.7節の「日用品は互いに見た目が違うので、形そのものが番号を担える」という論証は、
実装した物が実際にやっていることと逆になっている。

**直し方。** 表3の「断片は各128 bit」を「断片は秘密と同じ大きさ（実装では20.8 bit）」に直す。
3.7節は「実装では2-of-3を本立て3台に分け、番号は刻印で示した。担体の見た目を変えれば
形そのものに番号を担わせられる」と、実装と将来の設計思想を分けて書く。

### 誤り5（3.4節・187行目）　「スロット数を素数にとれば」は12スロットの実装と合わない

草稿の記述は次のとおりである。

> 誤り訂正にはリードソロモン符号を用いる。**スロット数を素数にとれば**、その素数を位数とする
> 有限体の演算をそのまま組むことができ、笛1本が計算上の1記号に対応する。

**判定は誤りである。** 3.2節が述べる実装のスロット数は12であり、12は素数ではない。
隣接同音禁止のもとで記号として使えるのは差分値の個数 m−1 = 11 であり、
素数体の位数はこちらの11である（`fue/cipher_codec.py` 291-305行目、
`p = _prime_below(m - 1)`）。旧版は13スロット（素数）だったのでこの文は正しかったが、
12スロットへ移した時点で成り立たなくなっている。

**直し方。** 「隣接同音を禁じたときの記号数（スロット数から1を引いた値）を素数にとれば」と
書き換える。12スロットなら11が素数なので条件を満たす、と続けるのが実装どおりである。

### 誤り6（2.5節・121行目）　128ビットを21×21に載せるのはCompactSeedQRである

草稿の記述は次のとおりである。

> SeedQR [40] はBIP-39の語を索引番号に写して二次元コードに収め、128ビットを21×21の格子に
> 載せて金属板に打刻する仕様である。

**判定は誤りである。** `raw2/v3-codex32-seedqr.md` の94行目と96行目に一次資料の内容がある。

- 標準のSeedQR：索引を4桁の十進数に零詰めして連結し、数値モードで符号化する。
  12語では48桁になり、**21×21には入らず25×25に収まる**。
- CompactSeedQR：索引を11ビットで連結して検査ビットを落とし、バイナリモードで符号化する。
  12語では**128ビット＝16バイトで21×21に収まる**。

草稿は前半（索引番号に写す）を標準SeedQRから、後半（128ビット・21×21）を
CompactSeedQRから取って1文にまとめてしまっている。

**直し方。** 「SeedQRは索引番号を十進で写して25×25に収め、その圧縮版であるCompactSeedQRは
索引を11ビットで連結して128ビットを21×21に収める」と分けて書く。
6.3節（351行目）の「70ミリメートル角の板1枚」もCompactSeedQRの数字なので、
そこでも版を明示したほうがよい（`raw2/v3` 218行目、`REVIEW_AND_REPOSITIONING.md` 199行目）。

### 誤り7（4.3節・255行目）　98.80パーセントと「実効長の約5パーセント」は比べられない

草稿の記述は次のとおりである。

> 2024年には離れた場所の市販の携帯電話の音響と磁界から軸方向の平均精度98.80パーセントに
> 達している [61]。本手法では半音1段が実効長の約5パーセントに対応するため、
> **この精度はスロットの粒度に迫っている。**

**判定は誤りである。** 98.80パーセントは「軸方向の移動・ステッピングモータの動作・
ノズル速度・ロータ速度の推定」の分類精度であって、長さの推定誤差ではない
（`REFERENCES_TO_ADD.md` 75行目、`raw/14-fab-security-privacy.md` 33行目）。
分類精度のパーセントと長さのパーセントを並べても比較にならない。

比較すべき数値は同じ調査記録の中にある。

- 2024年のJamaraniら：**平面的な設計で平均傾向誤差4.47パーセント**
- 2018年のChhetriら：軸推定精度86パーセントと並んで、**平均の長さ推定誤差11.11パーセント**

`raw/14-fab-security-privacy.md` の7行目は、まさにこの4.47パーセントを引いて
「CipherFluteは半音1段ごとに管の実効長を5パーセントから6パーセント変えるので、
この誤差は半音1段の差にほぼ並ぶ水準まで来ている」と書いている。

**直し方。** 「軸方向の平均精度98.80パーセント」を残すのはよいが、粒度の比較には
「平面的な設計で平均傾向誤差4.47パーセント」を使う。2018年の側は
「軸の推定精度86パーセント、長さの推定誤差11.11パーセント」と両方書くのが正確である。

## 2. 直したほうがよいが致命的でない点

### 2.1　「半音1段が実効長の約5パーセント」（4.3節・255行目）は5.6パーセントである

「実効長」を音響的な実効長（L + e）と読むなら、半音1段の比は 1 − 2^(−1/12) = **5.61パーセント**で
あり、較正定数によらず一定である。調査記録も「5パーセントから6パーセント」と書いている
（`raw/14-fab-security-privacy.md` 7行目）。

一方、側チャネルが実際に測るのは印刷される物理的な管長のほうである。実装の較正
（A = 87985.1、e = −10.010）で12スロット分を計算すると、隣り合う音の管長差は
1.67ミリメートルから2.97ミリメートル、割合では**4.2パーセントから4.7パーセント**である。

どちらに読んでも桁は合っているが、「約5パーセント」より「5から6パーセント」と書くか、
物理長で言うなら「半音1段で管長が約2ミリメートル、割合で約4.5パーセント」と書くほうが正確である。
`REFERENCES_TO_ADD.md` 141行目の「半音1段（管長でおよそ2ミリメートル台）」とも整合する。

### 2.2　「音域を半音1つ広げれば代償なしに手に入る」（3.4節・185行目）は現実装では成り立たない

符号理論としては正しい（13スロットで隣接同音を禁じた容量 log₂12 は、12スロットの
制約なしの容量と等しい）。しかし現在の実装は素数体を使うため、
`p = _prime_below(m − 1)` で m = 13 なら `_prime_below(12) = 11` となり、
1本あたりは log₂11 のままで増えない（`fue/cipher_codec.py` 291-305行目）。

**直し方。** 「符号理論の上ではそうなる。ただし本実装は素数体を使うため、
実際に代償ゼロにするには記号数が素数になる音域幅を選ぶ必要がある」と1文添える。

### 2.3　「記号数で割った余りを取る」（3.4節・185行目）は「スロット数で割った余り」である

`_diff_encode`（`fue/cipher_codec.py` 308-316行目）は `prev = (prev + 1 + d) % m` であり、
法は記号数 11 ではなくスロット数 m = 12 である。差分値 d の範囲が 0 から m−2 なので
記号数が11になる、という関係である。1語の直しで足りる。

### 2.4　Dabinらの数値の組み合わせ（2.3節・103行目）が原典の対応と違う

草稿は「印刷したリコーダーの**初版**が目標に対して+6から+34セント、
**やすりで手修正した版**が−13から+14セントであった」と書いており、
同じ楽器の改良前後のように読める。

原典の表1（`raw2/v2-printone.md` 139-155行目）では、+6から+34セントは**リコーダー1**、
−13から+14セントは**リコーダー2を手修正した版**であり、そのリコーダー2の手修正前は
−40から+1セントである。別々の楽器の数値を前後のように並べている。

**直し方。** 「印刷した2本のリコーダーが目標に対して+6から+34セントおよび−40から+1セントで
あり、指孔をやすりで手修正した版が−13から+14セントであった」と書く。

### 2.5　FluteCaseの79.7パーセント（2.2節・91行目）の帰属に注意が要る

79.7パーセントは原典に実在する数値である（`raw2/v1-whoosh-flutecase.md` 163行目）。
ただし原文は「8人の参加者と**14イベント**にわたる、一人を除いて学習する予備的な解析」であり、
この14イベントがFluteCaseの8本の管を含むかどうかは調査記録からは確定できていない
（記録自身は204行目でFluteCaseに帰属させているが、原文の根拠は示していない）。

**直し方。** 「Whooshの認識系は…利用者非依存では14イベントの精度が79.7パーセントに落ちる」と、
Whoosh全体の数値として書けば安全である。

### 2.6　「印刷のばらつき（実測でおよそ11セント）」（3.2節・167行目）は上界であって実測値ではない

5.1節（283行目）自身が「後者は吹き方のばらつきだけで説明がつく大きさであり、
造形そのもののばらつきは**多くとも**11セント程度と言える」と書いている。
3.2節で「実測で」と書くと、造形のばらつきを直接測ったように読める。
「多くとも11セント程度」と揃えるのがよい。

なお旧版3.2節は「標準偏差およそ10セント」であった。値を11に更新したこと自体は
5.1節と整合しており問題ない。

### 2.7　「刻み幅を残る誤差のおよそ4倍」（3.2節・167行目）の根拠が示されていない

旧版から引き継いだ設計の目安であるが、出典が本文にも調査記録にもない。
**確認できない。** 「設計の目安」と書いてある以上そのままでもよいが、
5.2節の残差±24セントを当てはめると 24×4 = 96 となり100セントに対する余裕はほとんどない。
どの誤差に対して4倍なのか（11.3セントの当てはめ残差なのか、15.2セントの吹奏ばらつきなのか、
±24セントの温度差条件なのか）を1文で特定したほうが安全である。

### 2.8　表記のゆれ

- 概要（19行目）と表1（149行目）は「3.5ビット」、3.6節（207行目）は「log₂11 ≈ 3.46ビット」である。
  正しい値は3.4594…なので両方とも誤りではないが、どちらかに寄せたほうがよい。
- 参考文献[48]（423行目）が「Smith, J. and Senturia, S.:（基準共鳴器との比による共通モード除去、
  1995年）」のままである。`raw3/c3-reference-resonator.md` に完全な書誌がある
  （James H. Smith and Stephen D. Senturia, "Self-Consistent Temperature Compensation for
  Resonant Sensors with Application to Quartz Bulk Acoustic Wave Chemical Sensors",
  TRANSDUCERS '95, pp. 724–727, DOI 10.1109/SENSOR.1995.721934）。

### 2.9　論文には影響しないが、実装側の注記が1つずれている

`fue/spool_128bit.py` の8行目は「128bit（16バイト）は**37記号**になり」と書いているが、
実際に符号化器を走らせると**38記号**である（11^37 は 2^128 をわずかに下回るため、
